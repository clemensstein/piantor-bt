Einen USB-Dongle für die Piantor Pro BT bauen

Ein nRF52840-Controller als zentraler Vermittler verwandelt die kabellose Split-Tastatur in ein Gerät, das sich am Host als kabelgebundene USB-Tastatur meldet — verfügbar ab dem Bootloader, ohne BLE-Latenz, bei spürbar längerer Akkulaufzeit beider Hälften.

Keyboard: Piantor Pro BT (Keebart) Controller: Seeed XIAO nRF52840 Firmware: ZMK

Eine ZMK-Split-Tastatur verbindet sich per Bluetooth über ihre Central-Hälfte mit dem Host. Beim Kaltstart steht diese Verbindung erst, wenn das Betriebssystem den BLE-Stack initialisiert hat — zu spät für Bootauswahl, BIOS oder einen verschlüsselten Boot-Prompt. Ein Dongle umgeht das: Er übernimmt die Central-Rolle, hängt per USB am Host und erscheint dort als HID-Tastatur, die ab dem Bootloader anspricht.

Der Umbau ist reversibel und erfordert keine Hardware-Änderung an der Tastatur. Beide Hälften werden zu Peripherals umgeflasht und funken nur noch an den Dongle; der Wegfall der Central-Rolle verlängert ihre Laufzeit deutlich. Der gesamte Firmware-Build läuft über GitHub Actions — lokal wird nichts installiert.

01

Einkaufsliste

Als Dongle eignet sich jedes BLE-fähige, von ZMK unterstützte Board. Der Seeed XIAO nRF52840 teilt sich Chip und Board-Target mit den Controllern in den Tastaturhälften und flasht per UF2-Massenspeicher, also ohne zusätzliche Werkzeuge oder Treiber.

Summe inkl. Gehäuse~18–28 €

Der XIAO ist eine Platine mit USB-C-Buchse, kein bündiger USB-A-Stick — er sitzt am Kabelende neben dem Host. Wer einen flachen Stick im A-Port bevorzugt, kann einen Nordic nRF52840 Dongle (PCA10059) verwenden; dieser bringt keinen UF2-Bootloader mit und wird über nrfutil geflasht, was den Erst-Flash aufwändiger macht. Der restliche Ablauf ist identisch. An der Tastatur selbst ändert sich nichts: kein Akku, kein zweiter Controller, keine Adapter.

02

Funktionsweise & Topologie

Im Standard-Split ist eine Hälfte Central (verbindet sich mit dem Host und empfängt die Events der anderen Hälfte), die andere Peripheral. Der Dongle wird zur neuen Central: Beide Hälften werden zu Peripherals, die ausschließlich an den Dongle funken, und der Dongle hängt per USB am Host.

Das Ergebnis ist eine Split-Tastatur mit dem Dongle als Central. Die Verbindung zum Host ist einfacher, da Dongles typischerweise per USB angebunden sind; die ehemalige Central-Hälfte gewinnt an Akkulaufzeit, weil sie zur Peripherie wird. zmk.dev — Keyboard Dongle

Latenzseitig verschiebt der Dongle die Rollen: Die ehemalige Central gewinnt einen zusätzlichen Hop (rund +1 ms über USB), während die Peripherals einen BLE-Hop gegen einen USB-Hop tauschen. Laut ZMK-Doku sinkt dadurch im üblichen Fall — Dongle am USB, Tastatur zuvor per BLE am Host — die durchschnittliche Latenz, weil bei den Peripherals rund 6,5 ms entfallen.

Gewinn

  • HID-Tastatur ab Bootloader/BIOS, keine BLE-Initialisierung nötig.
  • Längere Laufzeit beider Hälften.
  • Kein erneutes Pairing am Hauptrechner.

Kosten

  • Zusätzliches Board erforderlich.
  • Ohne Dongle ist die Tastatur funktionslos.
  • Einmaliger Konfigurations- und Flash-Aufwand.

Voraussetzung: Die Tastatur muss im regulären BLE-Betrieb ohne Dongle funktionieren. Das stellt sicher, dass spätere Probleme dem Dongle-Setup zuzuordnen sind und nicht der Tastatur selbst.

03

Config forken

Grundlage ist Keebarts offizielle Konfiguration für die Piantor Pro BT. Sie enthält Tastatur-Shield, Keymap, nice!view-Display-Konfiguration und den GitHub-Actions-Workflow — der Dongle wird additiv ergänzt.

  1. github.com/Keebart/zmk-config öffnen, Fork → Create fork.
  2. Im eigenen Fork lässt sich der Browser-Editor mit der Taste . öffnen (github.dev, VS-Code im Browser) — bequemer als die Standard-Oberfläche, aber nicht zwingend.

Sämtliche folgenden Änderungen erfolgen im Fork; jeder Commit löst automatisch einen Build aus.

05

Dongle-Shield

Der Dongle wird als reduziertes, privates Shield ohne eigene Tasten definiert, das aber Matrix-Transform und Physical-Layout der Tastatur referenziert, um Peripheral-Events auf Behaviors abzubilden. Vier Dateien im Ordner boards/shields/piantor/.

Kconfig.shield

Registriert das Shield. Vorhandene Datei ergänzen, sonst anlegen.

boards/shields/piantor/Kconfig.shield
# Kein Leerzeichen nach dem Komma, keines im Namen.
config SHIELD_PIANTOR_DONGLE
    def_bool $(shields_list_contains,piantor_dongle)

Kconfig.defconfig

Definiert das Shield als Central und legt die Peripheral-Zahl fest. Zwei Hälften → PERIPHERALS = 2. BT_MAX_CONN = Peripherals + gewünschte BLE-Host-Profile (Default 5); BT_MAX_PAIRED identisch.

boards/shields/piantor/Kconfig.defconfig
if SHIELD_PIANTOR_DONGLE

# Max. 16 Zeichen.
config ZMK_KEYBOARD_NAME
    default "Piantor Dongle"

config ZMK_SPLIT_ROLE_CENTRAL
    default y

config ZMK_SPLIT
    default y

config ZMK_SPLIT_BLE_CENTRAL_PERIPHERALS
    default 2

config BT_MAX_CONN
    default 6

config BT_MAX_PAIRED
    default 6

endif

piantor_dongle.overlay

Grundgerüst mit Mock-kscan — der Dongle deklariert eine leere 0×0-Matrix, da er keine physischen Tasten besitzt:

boards/shields/piantor/piantor_dongle.overlay
#include <dt-bindings/zmk/matrix_transform.h>

/ {
    chosen {
        zmk,kscan = &mock_kscan;
    };

    mock_kscan: mock_kscan_0 {
        compatible = "zmk,kscan-mock";
        columns = <0>;
        rows = <0>;
        events = <0>;
    };
};

Anschließend die Matrix-Transform der Tastatur in dieses Overlay übernehmen. Im Shield-Verzeichnis nach dem Node mit compatible = "zmk,matrix-transform"; suchen; er hat die Form:

zu kopierender Node (Werte tastaturspezifisch)
default_transform: keymap_transform_0 {
    compatible = "zmk,matrix-transform";
    columns = <12>;
    rows = <4>;
    map = <
        // RC(r,c)-Einträge
    >;
};

Den vollständigen Node als Kind des Root-Nodes (innerhalb / { … };) einfügen und das Label notieren (hier default_transform). Bei mehreren Transforms den zur Layout-Variante passenden wählen.

Für ZMK Studio zusätzlich das Physical-Layout einbinden — andernfalls entfällt dieser Schritt, die Tastatur bleibt voll funktionsfähig, nur ohne Studio-Editor. Node bzw. Datei über compatible = "zmk,physical-layout"; lokalisieren; bei Keebart liegt das Layout typischerweise in piantor-layouts.dtsi. Datei in den Shield-Ordner kopieren und referenzieren, Labels an die realen Namen angleichen:

piantor_dongle.overlay — Ergänzung
#include "piantor-layouts.dtsi"

&physical_layout0 {
    transform = <&default_transform>;
};

/ {
    chosen {
        zmk,kscan = &mock_kscan;
        zmk,physical-layout = &physical_layout0;
    };
};

Bei mehreren Physical-Layouts alle zugehörigen Transforms übernehmen und jeweils zuordnen.

06

build.yaml

Die build.yaml definiert die zu bauenden Firmware-Images. Sie erzeugt den Dongle, baut die settings_reset-Firmware mit und überschreibt die Split-Rolle beider Hälften per cmake-args auf Peripheral.

Die passenden Zeilen für die Dongle-Firmware ergänzen und an den bestehenden Tastaturteilen CMake-Argumente setzen, die sie zu Peripherals machen. Vor dem Flashen der neuen Firmware muss auf allen Geräten die settings_reset-Firmware geflasht werden, damit sie sich miteinander pairen können. zmk.dev — Building the Firmware
build.yaml
include:
  # Dongle (Central)
  - board: seeeduino_xiao_ble
    shield: piantor_dongle

  # Reset-Firmware fuer alle drei Geraete
  - board: seeeduino_xiao_ble
    shield: settings_reset

  # Linke Haelfte als Peripheral
  - board: seeeduino_xiao_ble
    shield: piantor_left
    cmake-args: -DCONFIG_ZMK_SPLIT=y -DCONFIG_ZMK_SPLIT_ROLE_CENTRAL=n

  # Rechte Haelfte als Peripheral
  - board: seeeduino_xiao_ble
    shield: piantor_right
    cmake-args: -DCONFIG_ZMK_SPLIT=y -DCONFIG_ZMK_SPLIT_ROLE_CENTRAL=n
Display-Shields beibehalten

Bei nice!view-Displays enthalten die Hälften-Zeilen Zusatz-Shields, etwa shield: piantor_left nice_view_adapter nice_view. Diese Bezeichner unverändert aus der Original-build.yaml übernehmen und nur die cmake-args-Zeile ergänzen — andernfalls bleiben die Displays dunkel.

Der Workflow unter .github/workflows/ reagiert auf jeden Commit; ein manuelles Pipeline-Setup entfällt. Status im Tab Actions: laufend (gelb), erfolgreich (grün), fehlgeschlagen (rot).

07

Build & Artefakte

Nach dem Commit unter Actions den aktuellen Lauf öffnen (Dauer ~2–5 min) und nach Abschluss firmware.zip aus den Artifacts laden. Inhalt:

firmware/
├── piantor_dongle-seeeduino_xiao_ble-zmk.uf2 # Dongle
├── piantor_left-seeeduino_xiao_ble-zmk.uf2 # links
├── piantor_right-seeeduino_xiao_ble-zmk.uf2 # rechts
└── settings_reset-seeeduino_xiao_ble-zmk.uf2 # Reset
08

Flashen

Flash-Vorgang je Gerät: per USB-C anschließen, Reset-Taster doppelt antippen (bei Hälften ohne Taster die Reset-Pins zweimal kurz brücken bzw. den im Keymap hinterlegten Bootloader-Trigger nutzen), woraufhin der UF2-Massenspeicher erscheint (XIAO-BOOT / NICENANO); die .uf2 darauf kopieren, das Volume unmountet nach Abschluss selbst.

Phase 1 — settings_reset auf alle drei Geräte

Die Reset-Firmware löscht die persistierten Bonds und stellt sicher, dass Dongle und Hälften sich anschließend sauber neu pairen. Wird sie ausgelassen oder nur partiell geflasht, finden sich die Geräte unter Umständen nicht.

settings_reset→ Dongle (XIAO)
settings_reset→ linke Hälfte
settings_reset→ rechte Hälfte

Phase 2 — Betriebsfirmware

piantor_dongle→ Dongle (XIAO)
piantor_left→ linke Hälfte
piantor_right→ rechte Hälfte

Seitenrichtig flashen: Vertauschen von Links/Rechts pairt zwar meist, spiegelt aber die Belegung.

09

Pairing & Test

Dongle per USB anschließen, beide Hälften in den Normalbetrieb versetzen (einschalten bzw. Ladekabel trennen). Die Verknüpfung erfolgt automatisch; der erste Aufbau kann 10–30 s dauern, danach zeigen die nice!view-Displays den Verbindungsstatus. Eingabe in einem Texteditor verifiziert die Funktion.

Pairing-Reihenfolge

Die Peripheral-Battery-Widgets ordnen sich nach der Pairing-Reihenfolge an. Für eine konsistente Anzeige nach dem Dongle-Flash zuerst die linke, dann die rechte Hälfte verbinden; bei mehr als zwei Peripherals von links nach rechts.

Funktionsnachweis für den Anwendungsfall: Neustart ins Bootloader-/BIOS-Menü — die Eingabe steht ohne BLE-Wartezeit zur Verfügung, da der Host eine kabelgebundene HID-Tastatur sieht.

11

Rückbau

Zum „Ent-dongeln“ genügt es, diese CMake-Argumente zu entfernen und die resultierende Firmware zu flashen — nach einem settings_reset. zmk.dev — Building the Firmware

Praktisch: cmake-args-Zeilen aus der build.yaml entfernen, neu bauen, settings_reset auf beide Hälften, anschließend die regulären Images flashen. Damit ist der direkte BLE-Betrieb wiederhergestellt.
